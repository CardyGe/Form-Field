# Form & Field — project audit and handoff

17 November 2026. Audited branch `map-stage-1`, HEAD `a6cb84a`, version `0.16.0`, 124 commits, including the pre-existing uncommitted changes. This was an audit: application source and the existing release app were not changed.

**Verdict:** Studio and Live have substantial working functionality and broad passing coverage. Map stage 2 is unfinished. The current branch must not be packaged for use until its missing native modules are included. Four product bugs were reproduced; two existing verification scripts also give misleading failures.

## Confirmed product findings

### 1. P1 — a newly packaged app cannot start

**Location:** `package.json:46–54`; `electron/main.cjs:9–10`; `electron/live.cjs:27`.

The explicit packaging file list includes `live.cjs`, but omits the new `output-window.cjs` and `map.cjs`. Main loads Live and Map unconditionally, and Live now imports the shared output-window helper. This affects the entire app, before a screen is opened.

**Reproduction:** built an isolated package under `work/audit-2026-11-17/package`. Packaging returned success, but inspection of `app.asar` confirmed both files were absent. Loading its Live module in Electron's Node mode failed with `MODULE_NOT_FOUND: ./output-window.cjs`. Adding that file alone would leave the missing Map module as the next startup failure.

**Fix:** include both runtime modules, preferably with a runtime-module inclusion rule that excludes tests, and make packaged startup a release check. A successful electron-builder run does not establish that the app can launch.

**Existing release distinction:** the existing `work/release` app is also labelled 0.16.0, but its native code predates Map and the shared helper. It does not contain those new imports. This finding concerns packaging the current branch, not proof that the existing installed app is broken.

### 2. P1 — Undo and subsequent edits can leave the projector showing the wrong composition

**Location:** `src/map/wall.ts:36–43`, `src/map/state.ts:26–32`, `src/map/messages.ts` (`sourcesToSend`).

Undo restores whole-show snapshots, including older source revision numbers. The sender notices the changed revision and sends the restored composition, but the wall rejects every revision less than or equal to its held revision. The wall's show metadata and saved composition can consequently describe a different picture from the one actually playing.

**Reproduction:** assign an instrument, change its six-colour palette (revision 1), then Undo (revision 0). The saved show restores the original palette; the wall stays on revision 1 and its changed palette. Make another palette edit: the saved source returns to revision 1, but the wall rejects that different composition too. Opening an older copy of a show with the same source IDs has the same underlying risk.

**Fix:** keep transport generations monotonically increasing across Undo, Redo, and document loads, independently of historical document revisions, or use explicit content identities/document sessions. Add tests covering the reducer, sender and wall together, including an edit after Undo and loading an earlier show.

**Evidence:** `work/audit-2026-11-17/reproduce.ts` and `revision-results.log`.

### 3. P2 — Live loses the last edit when the app closes before its debounce expires

**Location:** `src/ui/useLive.ts:103–113`; close-handler registration in `electron/preload.cjs`.

Live saves after 500 ms and has a fire-and-forget cleanup when its React screen unmounts. It does not register with the native `onBeforeClose` flush mechanism used by Studio and Map. Closing the app does not reliably run a React unmount and await that write. Save failures are also swallowed.

**Reproduction:** use the test-pattern source, wait for settings to save, change Movement response from 1 to 0.23, then close the app immediately. The input showed 0.23; closing completed in 161–168 ms across two runs; `live-settings.json` still contained sensitivity 1.

**Fix:** join the native close-flush protocol, await outstanding settings writes, retain failed pending changes, and report failures. Serialize native settings writes as well: the current writer uses one PID-based temporary filename without a queue.

**Evidence:** `work/audit-2026-11-17/ui-reproduce.mjs`, its isolated `ui-profile`, and `ui-results.json`.

### 4. P2 — Freeze is ineffective in Map's local preview

**Location:** `src/ui/MapPanel.tsx:95–109`.

With the output closed, Map runs a local compositor. The local draw inputs do not include `map.freeze`, and the compositor is never given `setFrozen(map.freeze)`. The button changes state while the instruments continue animating.

**Reproduction:** load Neon Shutters into a shape with no output window, press Freeze, and compare a 700 × 400 region one second apart after a settling delay. Freeze reported `aria-pressed="true"`, but approximately 16% of the sampled pixels changed. An isolated compositor test confirmed that calling `setFrozen(true)` itself holds the image exactly; this is missing UI wiring.

**Fix:** pass Freeze through the local compositor's current inputs and apply it on every local frame/state change. Cover both output-open and output-closed operation.

**Evidence:** `work/audit-2026-11-17/ui-results.json` and `gpu-results.json`.

## Verification problems

1. **Map's motion test samples too few pixels.** The original `scripts/verify-map.mjs` failed its moving-picture and resume-after-Freeze assertions. Both sample three fixed pixels in a broad, flat-colour preset. A full-region compositor check showed motion, exact freezing and resumed motion. A disposable copy using the script's existing 24 × 14 grid for those assertions passed all 12 checks. This does not fix or cover the local-preview Freeze bug above. Update the maintained test to measure change across a region, not three individual pixels.
2. **Studio's interaction test assumes the old Save behavior and message.** `scripts/verify-canvas-interaction.mjs:235` waits for `Project saved.` and assumes Save will open a dialog for `interactive.formfield`. It previously opened `fixture.formfield`, so the current app correctly saves back to that file and reports `Saved to fixture.formfield.`. Changing the expected toast alone still fails. The test needs Save As when it expects a new path, plus the current message or a file/state assertion. A focused disposable export check uses the existing Save As keyboard shortcut and the current confirmation to reach the save/open and PNG/movie checks.

All disposable copies live under `work/audit-2026-11-17`; the maintained scripts were left as found.

## Remaining checks and design risks

- The preset sweep proves basic rendering/numerical health at a small resolution. It does not re-approve every look's artistic quality, seamlessness, motion quality or 4K performance.
- No physical projector, real-person/camera qualification, prolonged show, multi-display stress test, or signing/notarization qualification was performed. Existing 60 fps records have specific synthetic-source and machine limitations; they are not a stage-2 Map benchmark.
- The uncommitted compositor limits active slots to 24 although a show can contain 64 sources. Slots are released when sources leave the show, but hidden sources retain theirs. Review hidden-source eviction, local-compositor disposal while the wall is open, and repeated open/close behavior before a long show. This is a static lifecycle concern, not a measured long-session failure in this audit.
- The editor accepts palettes of 2–8 colours while Studio's project validator requires exactly six. The current named UI palettes all contain six, so normal UI operation avoids this mismatch. Tighten the editor contract before exposing other palettes.
- The 24 MiB source-message limit is smaller than the base64 representation of a single allowed 20 MiB image, before counting masks or other layers. Revisit the size/error/acknowledgement contract when adding Edit in Studio or imported content. The current sender records rejected revisions as sent and a subsequent show message clears its warning.
- The README is stale in places: its generic current-limits paragraph still says there is no fluid simulation despite the newer Live work, and it does not explain current Map availability. Update the guide after defining the stage-2 release boundary.
- This was a local functional/code/package audit, not a vulnerability-advisory scan or exhaustive proof of correctness.
